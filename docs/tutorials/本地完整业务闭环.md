# 教程：在本地走完一张商用车售后工单

目标：在 20 分钟内亲手完成一次正常闭环和一次改诊补偿，并能指出每一步的业务不变量。默认使用脱敏示例数据，不需要模型 API Key 或外部数据库。

## 1. 启动

PowerShell：

```powershell
./scripts/bootstrap.ps1
./scripts/run.ps1
```

看到 Uvicorn 监听 `127.0.0.1:8000` 后，打开：

- 业务控制台：`http://127.0.0.1:8000`
- OpenAPI：`http://127.0.0.1:8000/docs`
- 健康检查：`http://127.0.0.1:8000/api/v1/health`

## 2. 正常闭环

### 2.1 创建工单

保持角色为“平台管理员”，选择“欧曼银河 9 · P20EE”，点击“创建服务请求”。页面应显示：

- `THREAD sr_...`：thread_id 与 service_request_id 相同；
- 状态 `TRIAGED`；
- Task Plan 版本 `V1`；
- Trace 中存在 `vehicle.decode_vin` 工具调用。

此时手机号不在工单 JSON 里，只有 `reporter_pii_ref`。这证明直接标识与 Agent 可见状态隔离。

### 2.2 运行初诊

点击“运行证据诊断”。状态变为 `WAITING_EXPERT`。检查诊断区：

- `mode_a_oem_special_tool` 表示燃油车专检模式；
- evidence 至少包含 FIM、SOP 或历史案例；
- 每条证据有版本和章节；
- `confirmed_code` 仍为空；
- 审批列表出现 `diagnosis.confirm`。

关键理解：系统已经有候选原因和候选件，但还没有确诊，因此不能进入配件履约。

### 2.3 专家确认

点击“专家确认初诊”。演示界面选择第一候选 DTC，并提交“证据与专检一致”。后端执行：

1. 校验诊断 ID，拒绝旧诊断的迟到确认；
2. 写入 `confirmed_code` 和 `confirmed_by`；
3. 完成 `expert_confirm` 任务；
4. 启动 `parallel_fulfillment` LangGraph；
5. 并行生成 dispatch 和 parts 候选；
6. 生成待审批的 `dispatch.assign`。

状态变为 `FULFILLING`，但此时仍不能开工。

### 2.4 调度审批与配件预占

点击“审批并预占资源”。流程先验证审批令牌，再由独立验证器检查候选，最后经 `workflow.assign_resource` MCP 工具建立 120 秒语义租约。

再点击“预占候选配件”。演示选择首个候选并启用 BRING_BOTH；若同时有原厂和副厂候选，会双路预占。

当且仅当以下条件同时成立时，状态进入 `READY_FOR_SERVICE`：

```text
selected_resource_id != null
AND reserved_part_codes is not empty
```

### 2.5 开工和结案

点击“现场开工”，状态进入 `IN_SERVICE`。再点击“提交结案”，工单停在 `WAITING_CLOSE_APPROVAL`。点击“专家审批结案”后才进入 `CLOSED`；专家也可驳回，使工单回到 `IN_SERVICE` 补充施工或路试证据。审批通过后产生：

- `knowledge.case_candidate_created`：案例只进入隔离区；
- `workorder.closed` Outbox 消息：供运营归档消费者处理；
- `archive` Task 成功，质量门禁仍标记离线复核。

## 3. 改诊与补偿

创建第二张工单，走到 `FULFILLING`、`READY_FOR_SERVICE` 或 `IN_SERVICE`。点击“模拟现场改诊”。

应观察到：

- 状态变为 `REDIAGNOSIS_REQUIRED`；
- `plan_version` 从 1 变为 2；
- `frozen_versions` 包含 1；
- 原 `selected_resource_id` 清空；
- 原 `reserved_part_codes` 清空，库存恢复；
- 时间线出现 `saga.compensated`；
- 初诊的 `confirmed_code` 被清空，必须重新诊断。

这条路径证明系统不会在“现场改诊”后继续执行旧件发运。

## 4. 新能源高压路径

选择 “DeepWay 深向星辰 · P0AA6” 创建工单。运行诊断后确认：

- 模式为 `mode_b_ev_manual_rag`；
- SOP 包含下电、验电、挂牌和绝缘检查；
- conflicts 提醒高压门禁；
- 调度候选全部包含 `hv_certified`。

如果候选没有高压资质，硬过滤会在优化之前将其排除，LLM 和 CP-SAT 都看不到这个非法候选。

## 5. 运营问数

在底部输入“当前工单量是多少？”，情景变化填 10。结果包含：

- `fact`：白名单指标真实计算值和样本量；
- `inference.label = hypothesis_not_fact`；
- `recommendation.status = pending_approval`；
- `scenario.label = what_if_not_fact`；
- `query_template`：`metrics.run_template(...)`，而不是自由 SQL。

## 6. 用 API 重做一次

先创建工单（为了清晰省略部分响应）：

```powershell
$headers = @{
  "X-User-Id" = "info-01"
  "X-Role" = "information_officer"
  "Content-Type" = "application/json"
}

$body = @{
  reporter_name = "王队长"
  reporter_phone = "13900000000"
  vehicle = @{
    vin = "LVBV6PDC8SM000901"
    brand = "foton_auman"
    model = "银河 9"
    power_type = "diesel"
    model_year = 2025
    configuration_code = "AUM-G9-YC6"
  }
  symptom = "重载后故障灯点亮，尿素消耗异常并偶发限扭"
  dtc_codes = @("P20EE")
  telemetry = @{ upstream_nox_ppm = 410; downstream_nox_ppm = 355 }
  service_mode = "oem_authorized"
  location = "佛山顺德"
} | ConvertTo-Json -Depth 5

$order = Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/v1/work-orders" -Headers $headers -Body $body
$order.service_request_id
```

然后在 Swagger UI 中按顺序调用 diagnose、expert-confirm、dispatch/approve、parts/reserve、service/start、close 和 close/approve。最后一步使用 `expert` 角色并提交待审批记录中的 token；注意每次切换正确的 `X-Role`。
