# Tutorial：一致性与故障注入实验

这组实验不追求“页面能点通”，而是验证面试官最容易追问的四个可靠性不变量：陈旧写不能覆盖、重试不能重复扣库存、连续故障会熔断、高风险结案必须可驳回。

## 准备

```powershell
.\scripts\bootstrap.ps1
.\.venv\Scripts\python.exe -m pytest -q
```

当前基线应为 25 项测试通过。下面每个实验都能在对应测试中找到可执行断言。

## 实验一：两个参与者同时修改一张工单

阅读 `tests/test_domain.py::test_repository_increments_version_and_rejects_stale_copy`。

1. 从 Repository 连续读取两次，得到相同 `version` 的两个深拷贝。
2. 第一个副本用 `expected_version` 保存成功。
3. Repository 在锁内把版本设为 `current.version + 1`。
4. 第二个副本仍携带旧版本，保存时抛出 `OptimisticLockError`。

关键点是版本在每次**聚合保存**时递增，而不是只在状态变化时递增。调度审批和配件预占可能都停留在 `FULFILLING`，但它们仍是两个独立写入，必须产生两个版本。

面试追问：“为什么不自动重试？”答：技术上可以重新读取，但业务上不能盲目合并资源分配和库存决定；冲突方应重新计算前置条件，再由用例层决定重试或提示。

## 实验二：库存预占请求超时后重试

阅读 `tests/test_full_workflow.py::test_parts_reservation_retry_is_idempotent`。

第一次预占把库存减一并记录 `order_id -> part_codes`。客户端假设响应丢失，以完全相同参数重试：

- 返回当前工单，不再次调用库存工具；
- 工单 `version` 不变；
- 库存仍只减少一件。

如果同一工单改用另一组配件重试，系统不会静默覆盖旧预占，而是要求先释放或走改诊补偿。生产实现应再用 `order_id + plan_version + action` 建唯一幂等键，响应快照持久化到数据库。

## 实验三：外部适配器连续失败

阅读 `tests/test_mcp_resilience.py::test_gateway_opens_circuit_after_three_tool_failures`。

工具连续失败三次后，网关为该工具打开 30 秒熔断器；第四次调用在进入 handler 前抛出 `CircuitOpen`。这避免故障中的 OEM、WMS 或地图服务被重试风暴进一步压垮。

同时验证：

- 限流按 actor 独立计数；
- 计数与熔断状态在线程锁内更新；
- 失败调用仍写审计记录；
- 嵌套对象和数组里的 `phone`、`token`、`approval_token`、`password` 都会被脱敏。

## 实验四：专家驳回结案

阅读 `tests/test_full_workflow.py::test_rejected_closure_returns_to_service`。

现场工程师提交结果后，工单只进入 `WAITING_CLOSE_APPROVAL`。专家使用审批 token 决策：

- 通过：进入 `CLOSED`，生成隔离区案例候选，并追加 `workorder.closed` Outbox；
- 驳回：审批记录固化为 rejected，工单回到 `IN_SERVICE`，任务恢复 running，可继续补充路试证据。

这说明 HITL 不是前端确认框，而是有角色 scope、一次性待审批记录、状态机边和审计时间戳的业务协议。

## 推荐演示顺序

面试现场先运行：

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_domain.py tests\test_mcp_resilience.py -q
```

再画出 `read V5 -> writer A saves V6 -> writer B rejected`，最后解释生产替换：PostgreSQL 条件更新、Redis/网关分布式限流、数据库唯一幂等键、Outbox 同事务落库。这样既能展示代码，也能主动说明样板与生产环境的边界。
