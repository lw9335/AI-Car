# Hybrid RAG 与证据链

## 1. 为什么商用车诊断不能只做向量检索

维修查询同时含有精确标识和语义描述：`P20EE`、VIN、品牌、车型、手册版本需要精确匹配；“重载后限扭、尿素消耗异常”需要语义召回；故障到部件的多跳关系适合图扩展。单一向量检索很容易召回语义相似但品牌或车型错误的段落。

本项目的检索顺序是：**先结构过滤，再并行召回，再融合重排，最后输出版本化证据**。

## 2. 查询构造

输入由以下字段组成：

- 症状原文；
- DTC 列表；
- `VehicleProfile.brand`；
- `VehicleProfile.model`；
- 配置码和年份在生产过滤器中进一步使用。

代码首先把中文拆为单字和双字片段，把字母数字标识作为整体 token。生产中 BM25 使用 OpenSearch analyzer，向量使用领域 embedding。

## 3. 四路能力

### 3.1 结构化过滤

候选必须品牌一致，且文档 `model` 为空（品牌通用）或与车辆车型相同。它是召回前的硬过滤，而不是结果出来后让 LLM“注意一下”。硬过滤能从根源上避免跨品牌证据污染。

### 3.2 词法召回

演示 `_lexical_score` 统计 query token 与标题、章节和正文重合。生产对应 OpenSearch BM25，特别适合 DTC、件号和标准术语。

### 3.3 向量召回

演示用 token 计数向量的 cosine 相似度表达语义近似。生产对应 pgvector 或向量引擎，适合“动力不足”等非标准描述。

### 3.4 故障图扩展

`FAULT_GRAPH` 从 DTC 扩展到可能原因，再依据扩展词命中文档。生产中 Neo4j 可表达 `DTC -> 故障域 -> 原因 -> 检查项 -> 部件 -> 工具` 的多跳关系。

## 4. RRF 和领域重排

不同检索器的原始分数不可直接相加。RRF 只使用排名：

```text
RRF(d) = Σ 1 / (k + rank_i(d)), k = 60
```

随后加入可解释的领域 bonus：

- DTC 命中：`+0.08`；
- FIM/SOP 权威源：`+0.04`；
- 精确车型：`+0.03`；
- 案例仅小幅加分，不能压过官方手册。

生产可把最后一步换成 cross-encoder reranker，但品牌、版本、安全等硬规则仍不能交给概率模型。

## 5. `EvidenceRef` 为什么必须结构化

每条证据包含：`evidence_id`、来源类型、标题、章节、品牌、车型、版本、分数和摘录。诊断假设只保存 evidence_id 列表，最终 UI 可以回溯具体内容。

“模型说参考了维修手册”不是证据链；“AUM-FIM-P20EE-2025-04，第 4.2 节，版本 2025.04”才是可审核引用。

## 6. 初诊包如何产生

维修 Agent 将证据变成结构化 `DiagnosisPackage`：

- `hypotheses`：候选 DTC/原因、置信度、推理摘要、安全级别；
- `sop_steps`：下一步检查顺序；
- `required_tools`：专检、绝缘表等；
- `candidate_part_codes`：只作为候选，不能直接出库；
- `conflicts`：版本或高压安全冲突；
- `requires_expert`：始终为 true。

最后一条很重要：即便内部置信度达到 0.88，也不能把初诊自动改成确诊。置信度只帮助排序和升级，不替代责任主体。

## 7. 无 DTC、OEM 不可用、证据冲突

- **无 DTC**：输出 `SYMPTOM_ONLY`，要求先读专检数据；不能猜件号。
- **OEM 工具不可用**：生产进入手册 RAG + 专家降级，标记 `degraded_mode`。
- **证据版本冲突**：写入 `conflicts` 并强制专家确认具体车辆配置。
- **新能源**：无论模型置信度如何，必须通过下电、验电、挂牌和持证人员门禁。

## 8. 知识回流防污染

结案不会直接把对话写回检索库，而是产生隔离区案例候选。后续需完成：PII 脱敏、字段完整性、证据一致性、专家质量评分、去重和版本发布。失败案例可以进入 Dataset，但不等于进入生产知识库。
