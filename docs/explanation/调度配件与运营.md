# 调度、配件与运营三个领域

## 一、服务资源调度

### 1. 场景先决定约束包

四类服务模式不是四套求解器，而是四个约束包：

- OEM 授权站：品牌授权、SLA 和现场支持优先。
- 散户/回头客：联系方式确认和快速响应优先。
- 合作修理厂：技术外派、工具协同和专家支持。
- 车队服务：批量车辆、驻点和时效保障。

`ServiceMode` 进入资源硬过滤，错误模式的资源不会进入优化器。

### 2. 硬约束与软目标分开

硬约束：可用、品牌、服务模式、动力类型、新能源高压资质。任何一项不满足就排除。

软目标：技能匹配、ETA、当前负载和履约稳定性。演示把它们归一化成 score，再乘 100 转成 CP-SAT 整数目标。

为什么整数？CP-SAT 工作在整数/布尔变量上，浮点分数要先缩放。生产要记录每个 objective term 和权重版本，保证结果可解释。

### 3. CP-SAT 在样例中的模型

每个候选一个布尔变量 `x_i`：

```text
Σ x_i = 1
maximize Σ objective_i * x_i
```

生产多工单排班会增加：工单—人员—工位—时间段变量、技能矩阵、班次、容量、路程、工具共享、时间窗和优先级。样例保留了同一求解机制，但不冒充完整车队排班规模。

### 4. 为什么还要独立验证器

优化模型可能因需求迭代漏加约束，也可能出现输入转换错误。审批后 `verify_assignment` 用独立代码重新验证候选存在性和 HV 资质。它不是重复浪费，而是高风险写操作的第二道防线。

### 5. 审批—预占—派工

候选只是建议。调度员选择后携 token 调用 Gateway；Gateway 校验 scope，才建立短租约。真实外部派工回执应成为履约真源，Redis 只负责并发预占，不能当长期工单数据库。

## 二、配件供应链

### 1. 为什么必须以确诊为门禁

维修初诊会列出多个假设。如果每个假设都直接触发配件，库存和物流会被大量错误占用。`PartsAgent.candidates()` 因此要求 `diagnosis.confirmed_code`，没有专家确认就抛业务错误。

### 2. 三层过滤

1. DTC/证据产生候选件号；
2. VIN、品牌、车型和配置校验兼容；
3. 库存和 ETA 决定履约优先级。

“大模型生成一个看似合理的件号”不在允许路径中。件号来自版本化知识或 BOM/配件主数据。

### 3. BRING_BOTH

现场不确定但停工成本高时，可以同时外带原厂和副厂件。两件都要真实预占，现场选择后核销一件、释放另一件。演示在 `bring_both=True` 时自动补齐同组原厂/副厂候选。

它不是默认策略：会占用库存并增加运输成本，生产应受客户授权、价格阈值和库存水位规则控制。

### 4. 改诊补偿

改诊后旧件可能处于“仅预占、已出库、运输中、已签收”不同阶段。演示只实现预占释放；生产 Saga 要按阶段调用不同补偿，并接受“取消失败需人工处理”这一合法结果。

## 三、运营决策

### 1. 指标语义层

用户说“结案率”“完成率”都映射到 `closure_rate`。语义层保存正式 metric_id、别名、单位和定义，避免同一词在不同页面计算不同。

LLM 只做口径选择和参数抽取，不生成自由 SQL。真正查询必须经过白名单模板和类型化参数。

### 2. RBAC 与 ABAC

RBAC 决定运营角色可调用 metrics；ABAC 再根据 region/tenant/fleet 过滤数据。演示只实现 `region`，生产还需行列级权限、敏感维度抑制和小样本防推断。

### 3. 四层输出

- Fact：查询结果、单位、样本量、范围。
- Inference：可能原因，标记 `hypothesis_not_fact` 和置信度。
- Recommendation：负责人、目标、观察窗、停止条件，状态待审批。
- Scenario：What-if 假设，标记 `what_if_not_fact`。

这种分层阻止模型把“如果配件到货缩短 10%”说成“配件到货已经缩短 10%”。

### 4. 效果追踪

生产中建议批准后生成运营任务，记录 owner、baseline、target、window 和 stop condition。窗口结束得到 EFFECTIVE/INEFFECTIVE 标签，进入评测 Dataset。不能只记录用户是否点了赞，因为建议可能听起来合理但业务无效。
