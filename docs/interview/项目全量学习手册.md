# RoadMind 项目全量学习手册

## 0. 你必须先形成的项目心智模型

RoadMind 不是一个“维修问答机器人”，而是一个把 AI 放进商用车售后业务闭环的协同平台。业务从故障上报开始，经总控协助、工单规划、证据初诊、专家确认、人员/工具与配件履约、现场维修、结案和知识沉淀结束。只有总控是交互式 Agent；诊断、调度、配件和运营是确定性领域能力，同一张 L0 工单是唯一业务真源。

背诵下面这句话前，先理解每个分句：

> 我把开放式理解与封闭式控制分开：交互式总控 Agent 负责持续对话并编排四个业务 Agent；WorkOrderPlanner 只生成受审计的 Task Plan；高风险、可恢复路径由 LangGraph、状态机和人工门禁控制。

## 1. 业务问题

### 1.1 原来的痛点

- 信息分散：报修电话、微信群、DMS 工单、专检结果、配件库存和工程师沟通互相割裂。
- 经验依赖：相同故障在不同服务站重复摸索，手册版本和案例质量不一致。
- 协同串行：诊断结束才找人，再查件；等待时间大于实际维修时间。
- 责任不清：AI 建议、专家确认、调度决定和现场结果没有统一时间线。
- 数据难回流：结案文本不能直接变成高质量知识，容易带入 PII 和错误结论。

### 1.2 为什么需要多个领域能力

这不是为了追求 Agent 数量，而是各域的目标函数和写权限不同：

- 维修追求诊断证据和安全，不能直接扣库存。
- 调度追求技能、ETA、负载与 SLA，最终选择属于调度员。
- 配件追求兼容、库存、到货和成本，必须以确诊为前提。
- 运营追求指标口径和效果追踪，不应接触逐单 PII。

把它们放进一个超级 Prompt 会造成上下文膨胀、权限混杂和难以测试。

## 2. 总体架构

### 2.1 入口与角色

FastAPI 是统一入口；控制台用 `X-Role` 模拟多角色。身份转成 `Principal(user_id, role, region)`，`require_scope` 做 RBAC。生产中 OAuth 验证在 API Gateway，MCP Gateway 对具体工具再做二次授权。

### 2.2 L0 工单

`WorkOrder` 聚合以下信息：

- 业务输入：车辆、症状、DTC、遥测、模式、位置；
- 当前事实：状态、确诊、已派资源、已预占件；
- 决策过程：候选、Task Plan、审批；
- 审计：timeline、version、plan_version；
- 恢复：replan_count、degraded_mode。

为什么把候选也放在聚合里？因为审批时必须验证“这个选择是否来自当时那一版候选”。生产大数据量时可以把候选拆表，但仍要绑定工单版本。

### 2.3 四层记忆

简历中的四层可以这样解释：

1. L0 业务真源：`WorkOrder` 的已确认事实和事件。
2. L1 领域草稿：`DiagnosisPackage`、dispatch_candidates、parts_candidates。
3. 会话摘要：生产中保存用户对话压缩结果，不能覆盖业务事实；样板未接真实 LLM 压缩器。
4. PII Vault：姓名/电话独立保存，L0 只有 opaque ref。

领域 Subagent 按次调用，是为了减少长期上下文串扰；每次只返回结构化结论，不把内部思维链写入 L0。

## 3. Parent 与 Task Plan

### 3.1 Parent 做什么

`understand()` 输出：intent、missing_fields、routed_domains、rationale。`plan()` 输出带依赖的任务图。

为什么工单规划器默认是确定性的？高风险售后任务图不应依赖模型版本和采样随机性。开放式员工交互由独立的 Enterprise Assistant 使用 Deep Agents SDK；工单规划器保持结构化、可审计并可离线测试。

### 3.2 Parent 不做什么

- 不直接修改库存或派工。
- 不跳过专家确认。
- 不自行决定状态机任意迁移。
- 不把内部自然语言当作业务事实。

### 3.3 计划版本

`plan_version` 解决迟到回调问题。假设 V1 的物流回执在现场改诊后才返回，此时工单已是 V2。消费者必须检查事件携带的 plan_version，不允许把 V1 的“已发货”写进 V2 当前状态，只能记为迟到事件并执行补偿/人工处理。

## 4. 诊断能力

### 4.1 输入归一化

真实入口可能有文本、语音、图片、视频、VIN、DTC 和 IoT 信号。样板直接接收结构化字段；生产前处理要把媒体解析结果连同来源、时间和置信度保存，不能只留模型总结。

### 4.2 Mode A / Mode B

- Mode A：燃油车，主机厂专检是故障码/引导测试真源；RAG 提供手册、案例和准备建议。
- Mode B：新能源，模型负责规划与工具调用，必须有手册 RAG、DeepWay/OEM 专家软件和 HV 门禁；远程不能指导带电拆装。

硬路由使用 `PowerType`，而不是让模型凭症状猜动力类型。VIN/配置优先级高于用户口述。

### 4.3 Hybrid RAG

你应能在白板写出：

```text
query = symptom + DTC
hard_filter(brand, model, version)
parallel: BM25 | vector | graph expansion
RRF(k=60)
domain rerank(DTC, authority, exact model)
EvidenceRef[]
```

当前向量是 token cosine 的可测试实现；生产换 embedding + pgvector。重点不是库名，而是不同召回通道的职责、分数融合和硬过滤位置。

### 4.4 初诊包

`DiagnosisPackage` 同时提供假设、SOP、工具、候选件、证据、置信度、冲突和是否需要专家。`requires_expert=True` 是固定规则。

置信度不是“正确概率”。它是多源信息充分程度的排序信号；若要校准成概率，需要有按车型/故障域标注的验证集做 reliability diagram、ECE/Brier 等校准。

### 4.5 冲突和降级

多手册版本、证据互相矛盾、低置信度或高压风险时升级专家。OEM 不可用时进入手册检索 + 专家，并明确 degraded_mode；不能生成一个 DTC 来填空。

## 5. 服务资源调度能力

### 5.1 三阶段

1. 候选：按技能、品牌、模式、区域、排班、资质硬过滤。
2. 优化：CP-SAT 综合技能、ETA、负载等软目标。
3. 决策：调度员确认沟通结果后，使用审批 token 预占和派工。

### 5.2 CP-SAT

样板中每个候选一个 BoolVar，exactly-one，最大化整数分数。生产多工单模型可以有：

```text
x[o,r,t] ∈ {0,1}
每个工单恰好一个主要资源
资源同一时间容量不超限
技能/证照/品牌/服务模式硬约束
工具和工位容量约束
到达时间满足窗口
minimize ETA + overtime + imbalance + reassignment_penalty
```

为什么不用 LLM 排班？LLM 不保证满足组合约束，也无法给出 optimal/feasible 状态。LLM 可解释需求，求解器负责约束优化。

### 5.3 Redis 租约

候选到正式派工之间用短租约防并发抢占。生产需要 NX+PX、续租 compare-and-set、释放 compare-and-delete。租约过期不等于业务派工撤销，长期事实仍在 PostgreSQL/DMS。

### 5.4 改派风暴

拒单、延误、失联会触发 redispatch。要设置 cooldown、最大次数、同一原因去重和人工接管，否则多个事件可能反复释放/抢占资源。

## 6. 配件供应链 Agent

### 6.1 主链路

确诊 DTC -> 故障域/原因 -> RAG/BOM 候选 -> VIN 兼容 -> 多仓 ATP -> 人工策略 -> 预占 -> 发运 -> 核销。

样板从证据中的 part code 和车型主数据开始，生产件号必须来自 OEM/BOM/配件主数据，不能让 LLM自由生成。

### 6.2 ATP

可用量不是表中库存数量：

```text
ATP = on_hand + inbound_callable - reserved - safety_stock
```

不同仓、在途可信度、承诺窗口和订单优先级都会影响 ATP。

### 6.3 BRING_BOTH

原厂+副厂双路外带适用于停工成本高、现场判断不确定的情况。代价是库存占用和物流成本，因此需要策略门槛。现场实选后一个核销、一个释放。

## 7. 运营决策 Agent

### 7.1 为什么不能自由 SQL

自由 SQL 有越权、注入、昂贵查询、口径漂移和数据泄漏风险。系统把自然语言映射到 formal metric_id，再调用参数化模板；权限过滤由服务端注入，模型看不到绕过选项。

### 7.2 事实、推断、建议

事实来自查询；推断是待验证假设；建议需要负责人和审批；What-if 是情景。输出 schema 把四类分开，避免语言混淆。

### 7.3 效果追踪

建议不是生成后结束。它要绑定 baseline、target、owner、window 和 stop condition，最终得到 EFFECTIVE/INEFFECTIVE 标签，回流 Dataset。

## 8. MCP Gateway

### 8.1 为什么 Agent-to-system 全过 Gateway

如果每个 Agent 直接集成 DMS/WMS，会复制认证、审计、限流、重试和错误映射。Gateway 是策略执行点和协议适配点。

### 8.2 调用顺序

工具存在 -> scope -> rate limit -> circuit -> 参数 -> trace -> handler -> audit。敏感字段如 token 在审计中替换为 `***`。

### 8.3 Tool annotation 为什么不是授权

annotation 是工具作者提供的提示，可能被篡改或错误配置。授权必须基于服务器端 principal 和 policy；模型说“这是只读工具”没有安全意义。

## 9. 一致性和恢复

### 9.1 乐观锁

Repository `save(expected_version)` 防止两个参与者基于同一旧状态覆盖。生产 SQL 通过 `WHERE version=?` 实现。

### 9.2 Saga

改诊跨人员租约、库存和物流，不能用本地事务回滚。补偿以相反顺序执行，并且每个补偿本身要幂等、可失败、可审计。

### 9.3 Outbox

工单与待发事件同事务；relay 重试发布；消费者按 message_id 幂等。同一工单用 service_request_id 分区保证顺序。

## 10. 可观测与评测

### 10.1 Trace 树

Root -> Subagent -> Workflow -> Tool。metadata 至少包含 service_request_id、plan_version、prompt_commit、knowledge_version、role。

### 10.2 评测不是一个总分

- 路由/抽取：准确率、F1。
- 检索：Recall@K、MRR、CitationHitRate、跨车型泄漏。
- 轨迹：工具顺序、审批、重试、补偿。
- 输出：faithfulness、可执行性、安全表达。
- 业务：不重复建单、不绕审批、不错误扣库存。

### 10.3 Engine 自进化边界

Engine 可对脱敏 Trace 聚类并建议 evaluator/修复，但不能自动改生产。修复需回归 Dataset、预发、人工门禁和灰度。模型不能同时当被测对象、裁判和发布者。

## 11. 代码导读

建议按以下顺序读：

1. `domain/models.py`：先知道系统保存什么。
2. `domain/state_machine.py`：知道哪些路径合法。
3. `application/service.py`：看一张工单如何跨域推进。
4. `agents/diagnosis.py` + `knowledge/retrieval.py`。
5. `agents/dispatch.py` + `agents/parts.py`。
6. `workflows/langgraph_flows.py`。
7. `mcp/gateway.py` + `mcp/tools.py`。
8. 测试：用断言确认你的理解。

## 12. 你应能现场画出的三张图

### 12.1 业务闭环

上报 -> 编排 -> 初诊 -> 专家 -> 调度/配件 -> 现场 -> 结案 -> 知识/运营。

### 12.2 控制架构

Parent（开放）在上，Workflow（封闭）在中，Domain/State Machine（真源）在下，MCP Gateway（副作用边界）在侧。

### 12.3 改诊时序

Mismatch -> freeze V1 -> cancel/release -> plan V2 -> clear confirmation -> rediagnose -> expert -> fulfill。

## 13. 项目优缺点

### 优点

- 不变量明确，正常/异常路径均可运行测试。
- Agent 与外部系统有清晰安全边界。
- 诊断、调度、配件、运营的领域差异真实存在。
- 离线可运行，同时为生产适配留出端口。
- 文档、测试和 OpenWiki 能互相校验。

### 限制

- 默认内存数据，无进程间一致性。
- RAG 语料很小，向量不是训练过的 embedding。
- CP-SAT 只做单次候选最优，不是大规模滚动排班。
- 没有真实 OEM/WMS/地图返回。
- LangSmith 云端和 Deep Agents 真实模型需要凭证。

面试时主动说限制，再给出具体迁移方案，远比模糊宣称“生产级”可信。
