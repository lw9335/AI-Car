## 5. 商用车项目：一条主线讲到底

### 5.1 一句话定位

RoadMind 不是维修问答机器人，而是把故障上报、初诊、人工确诊、人员和配件履约、现场维修、异常重规划、结案与运营回流串成一张可恢复工单的售后协同样板。

### 5.2 业务主链路

```text
报修建单
  → VIN/车型/症状/DTC 归一化
  → 生成 Task Plan
  → 初诊：硬过滤 + 多路检索 + EvidenceRef
  → 专家确认
  → [调度候选 || 配件候选]
  → 调度员批准并短租约占用 + 配件真实预占
  → AND Join 后允许现场服务
  → 结案申请 + 专家审批
  → 案例进入隔离区，质检后才可能沉淀
```

### 5.3 两个最重要的不变量

1. **初诊不等于确诊**：模型只能生成 DiagnosisPackage；没有专家确认，PartsAgent 不能进入配件履约。
2. **候选不等于副作用**：调度候选和配件候选只是草稿；派工需要审批 token，库存预占要验证候选、权限和幂等。

### 5.4 为什么总控、Workflow、Domain、Gateway 要分层

- 总控 Agent：处理开放式语言、缺失信息和粗路由。
- Task Planner：生成结构化、有依赖、有版本的任务图。
- LangGraph：固化并行、Join、中断、恢复和补偿流程。
- Domain/State Machine：守住“哪些状态能变到哪些状态”。
- MCP Gateway：统一执行工具发现、scope、参数校验、限流、熔断、Trace 和审计。

一句话总结：**LLM 负责理解，Workflow 负责过程，Domain 负责事实，Gateway 负责副作用。**

## 6. 三个主责模块必须讲透

### 6.1 售后服务总控 Agent

你的定位不是“写了一个会聊天的 Parent”，而是设计了企业总控的控制边界：

```text
员工请求 + Principal + conversation_id
  → 总控识别意图、补齐信息、选择领域
  → 按任务调用维修/调度/配件/运营 Subagent
  → Subagent 通过强类型工具调用共享 RoadMindService
  → 状态机、审批和 Workflow 校验
  → 结构化结果回写同一张 WorkOrder
  → 总控汇总并继续对话
```

必须能解释以下五个设计决定：

1. **为什么只有总控保持持续交互？** 它负责跨域目标和会话连续性；领域 Subagent 按次调用，只读取当前工单并返回结构化结果，减少跨工单上下文污染。
2. **为什么总控不等于 WorkOrderPlanner？** 总控处理开放式员工任务；Planner 只生成带依赖和版本的 Task Plan，默认确定性实现更容易审计和测试。
3. **为什么 Deep Agents 与 LangGraph 同时存在？** Deep Agents 适合开放式委派和工具探索；LangGraph 适合审批、并行 Join、补偿、interrupt/resume 等高风险固定流程。
4. **如何防止模型绕过人工门禁？** 写操作同时受到 `confirmed_actions`、角色 scope、状态机、审批 token、候选版本和 MCP Gateway 校验；Prompt 不是安全边界。
5. **记忆如何分层？** 对话/checkpoint 用于续聊，WorkOrder 才是确认事实，领域草稿绑定版本，PII 单独进 Vault。

当前真实边界：仓库同时有无模型可运行的确定性 Runtime 和可选 Deep Agents Runtime；真实模型路径依赖凭证。不要把确定性回退说成线上大模型效果。

### 6.2 MCP 集群与 Gateway

先把“集群”说准确：车辆、知识、调度、配件、运营是五个逻辑工具池；当前样板以独立 MCP Gateway 进程和统一 Tool Registry 验证协议与治理，生产可按故障域、数据主权和负载拆成多个 MCP Server。不要让面试官误解为已经部署了五套大规模 Kubernetes 集群。

完整调用链必须能一口气说清：

```text
总控/Subagent
  → 可选 server/discover / tools/list，或直接内联调用
  → 强类型 Tool Facade / MCP Client
  → Streamable HTTP / JSON-RPC 协议适配
  → Gateway.invoke
  → scope → rate limit → circuit → schema validation
  → Trace span → handler → redacted audit
  → 结构化结果或分类错误
```

项目采用 MCP `2026-07-28` 的无状态协议核心：不再执行 `initialize/initialized` 握手，也不依赖 `Mcp-Session-Id`。每个请求携带协议版本、客户端信息和客户端能力等 `_meta`，HTTP 请求同时用 `Mcp-Method` / `Mcp-Name` 暴露路由信息，因此请求可以被普通负载均衡分发到任意 MCP Server 实例，不需要 sticky session。`server/discover` 用于查询版本和能力，但客户端并非必须先调用它。

“协议无状态”不等于“业务无状态”。工单状态仍由 PostgreSQL/DMS 等业务真源保存；跨调用上下文使用显式的 `service_request_id`、`thread_id`、`plan_version` 或工具返回的 handle 传递，不能藏在传输 Session 里。

三个高频取舍：

- **为什么不是每个 Agent 直连 DMS/WMS？** 否则会复制认证、重试、审计、错误映射和限流逻辑，并让工具权限散落在 Prompt 中。
- **MCP Gateway 和 API Gateway 有何区别？** API Gateway 管网络入口、路由和通用身份；MCP Gateway 还理解工具发现、schema、tool-level scope、风险级别、调用审计和 Agent 工具语义。
- **Tool annotations 为什么不授权？** annotation 只是工具描述；真正授权来自服务端 Principal、scope、资源属性和审批事实。

失败处理要能具体说：参数错误、权限拒绝、业务错误、限流和熔断应分类；连续基础设施失败可打开 circuit；敏感参数在审计中递归脱敏；写工具必须有幂等键或业务侧唯一约束。

### 6.3 LangSmith 全链路观测与评测

观测目标不是“看到了 Prompt”，而是回答一张工单为什么失败、失败发生在哪一层、是否绕过审批：

```text
Root：一次员工请求/工单目标
  ├─ Subagent：维修、调度、配件、运营委派
  ├─ Workflow：审批、并行 Join、改诊补偿
  └─ Tool：具体 MCP 调用
```

关键 metadata：`service_request_id`、`conversation_id/thread_id`、`plan_version`、`prompt_commit`、`knowledge_version`、角色、工具风险和部署版本。父子 span 负责结构，业务 ID 负责跨服务关联。

必须讲清三层价值：

1. **排障**：看错误路由、工具静默失败、Join 不完整、重复调用和延迟来源。
2. **合规**：用轨迹 evaluator 检查敏感工具前是否存在有效审批、是否消费了正确 token、是否发生跨车型证据泄漏。
3. **迭代**：脱敏 Trace/负反馈进入 Dataset，形成 Golden Set；修改 Prompt、Context 或检索参数后离线回归，不低于基线才进入预发和人工灰度。

不要把一个总分当质量：路由、检索、轨迹、输出和业务不变量分别评测，其中“不绕审批、不重复扣库存、不把旧 plan 回调写入新计划”优先级最高。

当前真实边界：代码中真实存在本地 `TraceRecorder`，利用 ContextVar 形成父子 span，并在 Agent/Workflow/Tool 层记录；LangSmith 云端镜像、Engine 聚类和生产 Dataset 流程属于可选集成/设计方案，没有凭证和生产 Trace 时不能说已在线运行。

### 6.4 对领域 Agent 的正确口径

主责不是等于完全不了解领域能力。你必须能解释每个域的输入、输出、门禁、失败如何回到总控：维修输出带证据的初诊包；调度输出候选并等待人工审批；配件以专家确诊为硬门禁；运营只运行白名单指标。除非你确实负责具体算法，否则不要主动深入宣称 RRF 参数、CP-SAT 大规模排班或真实库存策略是你的主责。

## 7. 十二道核心追问

每题先遮住提示口述 60–90 秒，再按四项评分。

### 1. 总控 Agent 到底负责什么，不负责什么？

关键词：理解、补信息、跨域委派、上下文、结果汇总；不直接确诊、不直接选人、不绕审批、不把自然语言当业务事实。

### 2. 为什么不是一个大 ReAct Agent？

关键词：上下文膨胀、权限混杂、结果不确定、难恢复、难测试。总控开放，领域工具最小权限，高风险路径固化。

### 3. 总控 Parent、WorkOrderPlanner、LangGraph 三者有什么区别？

关键词：开放式交互；结构化任务 DAG；可恢复固定流程。分别对应理解、计划和执行控制。

### 4. Subagent 为什么按次调用？长期记忆放哪里？

关键词：减少跨工单污染；会话摘要用于续聊；WorkOrder 是事实；checkpoint 是执行状态；PII 独立保存。

### 5. 模型怎样被阻止绕过专家确认和写操作审批？

关键词：`confirmed_actions`、RBAC scope、状态机、审批 token、候选/版本校验、Gateway；Prompt 不算安全措施。

### 6. 为什么需要 MCP Gateway，不能让 Agent 直接调用业务 API？

关键词：统一工具发现、schema、scope、风险、限流、熔断、Trace、审计和协议适配。

### 7. 你说的 MCP“集群”到底是什么？

关键词：五个逻辑工具池；当前一个独立 Gateway/Registry 样板；生产按域和负载拆多个 Server；不虚构五套生产集群。

### 8. 从总控发起一次工具调用，完整链路是什么？

关键词：发现 → facade/client → 协议 → Gateway policy chain → handler → structured result/audit。

### 9. MCP Tool annotation 为什么不能作为授权依据？

关键词：annotation 是不可信提示；服务端 Principal、scope、资源属性和审批事实才是授权依据。

### 10. LangSmith Trace 树如何把 Agent、Workflow 和 Tool 串起来？

关键词：parent/child span + service_request_id/thread_id + plan_version；跨服务传播关联 metadata。

### 11. 你如何用 Trace 发现“遗漏审批”或“工具静默失败”？

关键词：轨迹 evaluator 检查敏感 tool 前置 approval；工具必须有终态、耗时、错误分类；业务事件与 span 对账。

### 12. 当前观测方案哪些真实实现，哪些仍是生产设计？

关键词：本地 TraceRecorder、父子 span、Agent/Workflow/Tool metadata 已实现；LangSmith 云端、Engine、真实生产 Dataset 需凭证和生产接入。

## 8. AI 应用开发基础速查

### Python / FastAPI

- `async` 适合等待网络/数据库 I/O，不会让 CPU 密集任务自动变快；CPU 重任务放进工作进程或任务队列。
- Pydantic 用于输入输出 schema 和边界校验；领域规则不能全部塞进路由函数。
- 依赖注入可统一认证、数据库会话和服务装配，便于测试替换。
- 异常应映射为稳定 HTTP 状态与错误结构，不能把内部堆栈直接返回给客户端。

### PostgreSQL / 一致性

- 乐观锁通过 `UPDATE ... WHERE id=? AND version=?`；更新行数不是 1 就说明发生并发冲突。
- 事务只保证本数据库内原子性，无法直接回滚已发生的物流、库存或外部派工。
- Outbox 要与业务事实同事务写入；relay 可重复投递，消费者必须按 message_id 幂等。

### LLM API / Prompt / Tool Use

- 结构化输出仍需服务端 schema 校验，不能因为模型“答了 JSON”就信任。
- 工具调用至少要有超时、重试边界、幂等、授权、审计和错误分类。
- Prompt injection 不能只靠系统提示解决；工具白名单、数据隔离和服务端权限才是安全边界。
- Context 不等于 Memory；会话摘要用于续聊，确认事实必须落业务库。

### SSE

- SSE 是服务器到浏览器的单向流，适合 token/进度事件；基于 HTTP，断线可重连。
- 需要高频双向通信时考虑 WebSocket；业务命令仍应走可审计 API，而不是把流连接当事务。

### Docker / 部署

- 当前 Compose 拆分 web、api、mcp-gateway、postgres、redis。
- 容器化不等于生产就绪；仍需健康检查、配置/密钥、日志、限额、滚动升级和持久化策略。

### Agent Eval

- 单步：路由、抽取准确率。
- 检索：Recall@K、MRR、CitationHitRate、跨车型泄漏。
- 轨迹：工具顺序、审批、重试、补偿。
- 输出：faithfulness、可执行性、安全表达。
- 业务不变量：不重复建单、不绕审批、不错误扣库存。业务不变量优先级最高。

## 9. 航空项目的安全讲法

### 60 秒版本

> 航空项目的核心是把维修数据、手册和工程资产统一成可治理的语义对象，再让 GraphRAG 和工程 Agent 在同一套权限与血缘上下文中工作。我重点参与的方向是维修 GraphRAG、FDE 的 Agent Loop，以及 Langfuse/DeepEval 的评测设计。GraphRAG 先抽取机型、ATA 和故障码，在召回前做机型隔离，再组合 local/global 图检索、向量补段和重排，最终引用 AMM、FIM、IPC 或案例 ID。FDE 不直接改生产，而是在 feature branch 上生成 Ontology/Pipeline 变更，经过 Preview、Validate、CI 和专家审批后合并。我的边界是：当前能详细说明架构、数据对象、控制流程和评测方案；没有证据的航司生产规模和商业系统接入我不会编造。

### 四个必答追问

1. **Ontology 是什么？** 不是普通术语表，而是把飞机、机型、ATA、系统、部件、故障、工卡、维修事件定义成带属性、关系和动作的统一业务对象层。
2. **为什么 GraphRAG？** 航空排故天然包含系统—部件—现象—原因—措施—案例的关系链；图检索补关系路径，向量检索补文本段落，两者都必须受机型/版本硬过滤。
3. **FDE 和裸 ReAct 有何区别？** Planner 只读探查，Executor 通过受控工具写 feature branch，Critic 对照 Preview/CI 审查；生产合并有人工门禁。
4. **为什么不能只用 LLM Eval 放行？** Ontology/Pipeline 是工程变更，必须有 schema、lineage、构建和回归校验；LLM 评分不能证明工程产物可运行。

## 10. 行为题准备

### 最大挑战

不要说“模型效果不好”。说：最难的是定义模型结论什么时候不能继续驱动真实动作，因此建立了确诊门禁、派工审批、配件幂等和改诊补偿。

### 一次失败

可以用今天的真实发现：测试资料仍写旧数量，完整回归出现挂起。这暴露了“文档口径和当前代码状态没有同步”。你的处理方式应是先承认、定位到具体路径、缩小复现、再修复并建立 CI 超时和结果基线。不要假装已经修好。

### 你个人做了什么

用“对象 + 动作 + 证据”回答：

> 我主要负责总控 Agent、MCP 工具集群和 LangSmith 全链路观测三部分。具体来说，我把总控的意图理解、领域委派、会话上下文和人工确认边界落成 Runtime 与强类型工具；把五域工具统一收口到 MCP Gateway 的发现、scope、参数、限流、熔断、Trace 和审计链；再用 service_request_id、plan_version 等 metadata 串起 Root、Subagent、Workflow、Tool，并设计轨迹合规和业务不变量评测。领域 Agent 的算法由对应模块承担，我负责它们与总控、工具层和观测层之间的契约与协同。

避免只说“负责整体架构”“参与了平台建设”。
